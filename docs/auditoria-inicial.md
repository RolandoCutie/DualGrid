# Auditoría técnica inicial de DualGrid

Fecha: 2026-11-13

## Alcance y método

Revisión del stack declarado y trazado de facturas/contratos, autenticación de backoffice, modelos CRM/proyectos/gastos y tres endpoints de formularios públicos: modelos Mongoose, validación Zod, páginas administrativas, API REST, agregados financieros y generación de PDF. No se inspeccionaron los valores de `.env` ni `.env.local`. Este documento registra hechos comprobados; no representa una auditoría de seguridad ni funcional completa de cada módulo del repositorio.

## Stack comprobado

- Next.js 16.1.6 App Router, React 19.2.3 y TypeScript 5 con modo estricto según `package.json` y `tsconfig.json`.
- Tailwind CSS 4; componentes propios y dependencias como Radix UI, Headless UI, CVA y Lucide.
- MongoDB con Mongoose 9. Los modelos están en `database/`; las rutas REST en `app/api/`.
- Sesión administrativa propia con HMAC y cookie HTTP-only; los endpoints de facturas y contratos verifican token en servidor.
- PDF server-side mediante `@react-pdf/renderer`.
- Resend está instalado y se utiliza para notificaciones de renovación; el envío de notificaciones para formularios públicos está pendiente de rastreo.
- Las credenciales y la clave HMAC tenían valores de desarrollo como fallback. Tras el hallazgo, la autenticación y validación de sesiones se endurecieron para fallar cerradas en producción si faltan las variables requeridas.
- No se declara script de pruebas ni dependencia de testing en `package.json`; por tanto, no hay una suite ejecutable identificada en esta inspección.

## Relaciones de datos observadas

- `Invoice.clientId` referencia `Client` y es obligatorio.
- `Invoice.contractId` referencia opcionalmente un `Contract`; cada contrato apunta a un `Client` mediante `Contract.clientId`.
- No existe modelo de pagos ni tabla intermedia factura-contrato.
- `Contract.paidAmount` se recalcula desde facturas cuyo estado es `paid`, no desde pagos; una factura solo puede sincronizar un contrato.
- Las facturas tienen soft delete (`deletedAt`) y número generado mediante contador atómico.
- Las líneas conservan descripción, cantidad, precio unitario y total; no se observó versionado o snapshot de catálogo asociado a la factura.
- `Project` es independiente de `Client`/`Contract`; `Expense` admite un `clientId` opcional y guarda importes como `Number`.

2. Completar la integridad del formulario/API: asociación múltiple factura-contrato con asignación clara de líneas/importes, preservando `contractId` histórico; cubrir la relación con pruebas de integración.
3. Introducir pagos como registros separados y estados documentales/de cobro compatibles; actualizar dashboard, listado, sincronización de contratos y PDF.
4. Investigar y reproducir el error de edición y el estado «Enviada» antes de atribuir una causa definitiva; validar persistencia tras recarga.
5. Guardar snapshots de emisor/cliente en documentos emitidos y alinear presentación previa/PDF, evitando cambios retroactivos.
6. Completar auditoría de permisos endpoint por endpoint, contratos, planes públicos, gastos/reportes y despliegue; implementar pagos, cotizaciones, configuración, cola de correo, proyectos operativos y auditoría con migraciones aditivas y pruebas.

## Cambios y verificación de esta etapa

- Contratos: `GET /api/contracts` admite `clientId`; el formulario los consulta al seleccionar cliente, muestra carga/vacío/error y ofrece continuar sin contrato. La creación y edición validan en servidor la propiedad del contrato. `contractId: null` permite desasociarlo sin borrar datos históricos.
- Edición/listado de facturas: la edición ya no carga todos los contratos. La lista muestra errores al persistir estados y refresca los datos server-rendered tras una respuesta exitosa.
- Seguridad: autenticación/sesiones fallan cerradas en producción sin credenciales y secreto HMAC explícitos. El PDF devuelve un mensaje genérico en errores internos.
- Sitio público: las tarjetas de planes web indican en inglés y español que hosting y dominio se cotizan por separado; precios y características no cambiaron.
- ESLint focalizado: correcto.
- TypeScript completo (`tsc --noEmit`): correcto.
- Build de producción (`npm run build`): correcto. Next muestra el aviso de que una ruta con Edge Runtime no puede prerenderizarse estáticamente.
- `git diff --check`: sin errores reportados.
- No se pudieron probar con datos reales la persistencia tras recarga, asociaciones inválidas, generación de PDF ni flujos de pago: no hay suite de testing declarada y no se ejecutaron operaciones contra MongoDB.

## Límites y decisiones pendientes

- No se ejecutaron migraciones, no se escribieron datos y no se inspeccionaron secretos.
- No se presupone jurisdicción fiscal ni se configura una tasa tributaria.
- La autenticación en producción ahora exige variables explícitas; falta verificar la configuración real del entorno de despliegue, que no se inspeccionó.
- La conversión de monedas y el método de cálculo/orden de impuestos requieren una política configurable; no se deben sumar monedas distintas.
- Rehacer o reescribir facturas/contratos ya emitidos puede tener consecuencias legales y requiere revisión profesional. Los cambios de esquema deben preservar documentos existentes.
- Este diagnóstico es una primera entrega previa a los cambios funcionales. Las áreas marcadas para auditoría posterior no deben considerarse aprobadas ni libres de defectos.
